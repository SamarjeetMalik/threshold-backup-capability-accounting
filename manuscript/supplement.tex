\paragraph{Tests.}
Twenty-seven tests in three files (\fpath{test_datalayer.py}, \fpath{test_datalayer_v404.py} and \fpath{test_datalayer_v409.py}) cover the following:
\begin{itemize}
\item round trips, including the empty object;
\item tampered, reordered, duplicated, appended and cross-object chunks;
\item truncation with and without the flag; missing, duplicated and early final markers;
\item partial failures, which release no plaintext;
\item abandonment, retry and identifier re-sampling;
\item canonical-encoding aliasing and malformed or foreign records;
\item the counts of Table~\ref{M-tab:counts};
\item a forced derived-key coincidence, which the key-byte guard reports as nonce reuse;
\item removal of one, two or three final chunks; removal of every chunk of a non-empty object, distinguished from the legitimate empty object; a modified immutable header; a forged final chunk in a non-final position and a non-final chunk in the final position;
\item forty objects stored concurrently from eight threads, with no key-nonce pair reused and every object round-tripping, and the per-instance scope of the guard.
\end{itemize}

\paragraph{Measurements.}
Wall-clock measurements of one Python process on one machine: Apple M5, 24~GiB, macOS 26.5.1, Python 3.12.14, pyca/cryptography 50.0.2 with OpenSSL 4.0.3.
\begin{itemize}
\item Inputs are seeded and identical across ciphers.
\item Each measurement follows five warm-up runs, with 40 repetitions per microbenchmark and 12 trials per object operation.
\item We report medians with interquartile ranges; raw samples are in the artifact.
\item These figures describe this machine only and enter no proof.
\end{itemize}
The timings come from \fpath{bench_v404.py}; raw samples are in \fpath{artifact/evidence_v411/mac_m5}. HMAC derivation took $0.96\,\mu$s (median; IQR $0.92$--$1.00$). ChaCha20-Poly1305 reaches $2.0$--$2.2$~GiB/s from 16~KiB chunks upwards (Fig.~\ref{fig:latency}). AES-256-GCM, measured on identical inputs as an engineering comparison, reaches $8.4$--$8.9$~GiB/s from 64~KiB upwards on this processor, which reports the ARMv8 AES and polynomial-multiply instructions (FEAT\_AES, FEAT\_PMULL); ChaCha20 has no dedicated instructions. This comparison is about speed on one machine, not about relative security, and the profile is unchanged: the paper's analysis is for ChaCha20-Poly1305, and a change of AEAD would need its own multi-key bound. Store and Open scale linearly with object size, about $124$ and $129$~ms for 256~MiB (Fig.~\ref{fig:objects}). An independent run of the same script on the same machine, kept in \code{artifact/evidence\_v404}, agrees within $8\%$ for ChaCha20-Poly1305 throughput from 16~KiB and AES-256-GCM throughput from 64~KiB; Store and Open at 256~MiB were $8$--$10\%$ slower there. Below 64~KiB the AES-256-GCM medians of the two runs differ by up to a factor of two, so small-chunk AES values are not stable on this machine. The measured ciphertext overhead equals the analytical 16 bytes per chunk.

Memory was measured with seven independent trials per object size (\fpath{bench_memory_v410.py}; raw data in \fpath{evidence_v411/mac_m5_memory}). In each trial one fresh process stores the object and writes the record to a file, and a second fresh process loads the record, starts \code{tracemalloc}, opens the object once and reads \code{getrusage(RUSAGE\_SELF).ru\_maxrss}. Python heap is the \code{tracemalloc} peak during Open. Resident set size is the peak over the opening process's lifetime, not a sampled value, and includes the interpreter and imported modules (an idle process peaks at $28.7$~MiB) and the loaded ciphertext. All memory figures are in MiB ($2^{20}$ bytes) and give the median with minimum and maximum over the seven trials; times give the median with interquartile range. Python heap was identical in every trial: $1.00$~MiB for a 1~MiB object and exactly twice the object size from 4~MiB upwards. The factor of two is the reference's Open path, which keeps the list of decrypted chunks and then joins them into one plaintext; the ciphertext was loaded before tracing started and is not in this figure. Peak resident set size was $807.9$~MiB in the median for 256~MiB (range $807.8$--$808.2$), consistent with interpreter, ciphertext and two plaintext copies. This is a property of the in-memory reference, not a lower bound for the design. All timings and memory figures in this section are for direct calls; they exclude the process supervisor, whose cost is in Section~\ref{sec:s-supervisor}. Concurrent and streaming measurements were not made.

\paragraph{Liveness counterexamples.}
Observation~\ref{M-obs:liveness} states that each fairness assumption is necessary. With weak fairness everywhere (\code{V401AllWF}), crashes and restarts alternate forever, so \code{SignReceipt} is never continuously enabled. Without fairness for \code{Erase}, \code{SignReceipt} or \code{Restart} (\code{V401NoErase}, \code{V401NoReceipt}, \code{V401NoRestart}), the respective step is never taken. Without fairness for \code{WorkerReturns}, an aborting worker never returns; with one request (\code{V401NoWorkerMin}), the essential steps are \code{Request}, \code{HoldCompletes}, \code{OfferCertificate}, \code{BeginDecrypt}, \code{BeginExpiry}, \code{Erase}, then stuttering. TLC does not minimize liveness traces, and the printed lassos also contain irrelevant environment steps.

\paragraph{Lifecycle induction.}
The safety invariants of the lifecycle also follow by a manual induction for arbitrary finite positive path and request domains.
\emph{Helper facts.} Receipts imply tombstones, absent slots, no buffers and no aborting or decrypting work on the path. A committed barrier requires its receipt and the barriers of earlier epochs. Buffers belong only to queued or sending jobs. Tombstones grow, and activated configurations do not decrease.
\emph{Cases.} Initialization has no work, receipts or barriers. \code{Request}, \code{OfferCertificate}, \code{HoldCompletes}, endpoint mutation and identity compromise transfer no data, and request identifiers are not reused. \code{BeginDecrypt} checks liveness, exact binding, configuration and hold; \code{FinishDecrypt} and \code{Transfer} recheck them. \code{BeginExpiry} persists the tombstone and moves owned work to cancelled, or to aborting if it is decrypting, and removes buffers, all atomically. \code{WorkerReturns} moves aborting to cancelled, and \code{WorkerAbandons} moves decrypting to cancelled; neither produces output or changes buffers. \code{SignReceipt} requires slot absence, no buffers and no aborting work; since decryption cannot begin on a tombstoned path, no decrypting work exists either, so the receipt helper fact is preserved. \code{Commit} requires the receipt and all earlier-epoch barriers, so the floor cannot decrease or advance prematurely. \code{ConfigUpdate} cancels or aborts work before changing the version. \code{Crash} ends all workers and buffers while preserving durable state. With the guard, \code{RollbackRestart} is admitted only before any tombstone, configuration or floor progress. \code{Transfer} is the only release, and its guard gives both release properties.
These cases establish the invariants under the abstract certificate, log and anchor contracts. This is a manual induction, not a TLAPS proof; TLC checks the instances in Table~\ref{tab:tlc}.

\paragraph{Conformance step statistics.}
One kernel call can perform what the specification models as consecutive actions, so a call is matched by a short sequence of specification steps rather than exactly one. The bound of three is a search depth, not a tolerance: the post-call abstract state must \emph{equal} a state reached from the pre-call state by legal specification actions. Every matched call is therefore a legal stuttering or multi-step move of the specification, and the safety invariants that TLC checks on all reachable specification states hold after it. Of the 80,000 calls of the reference kernel, 69,987 left the abstract state unchanged, 9,987 matched one step and 26 matched two; none needed three. Of the 77,126 calls of the baseline kernel (Observation~\ref{M-obs:conformance}), 67,289 left it unchanged, 9,588 matched one step and 34 matched two, and none needed three. The baseline kernel's 215 divergent schedules split into 212 certificate acceptances on a cancelled request, one duplicate completion, one stale abandon and one out-of-order barrier commit.

\section{Process supervisor and model correspondence}\label{sec:s-supervisor}

\paragraph{Tests.}
Ten tests (\fpath{test_worker_supervisor.py} and \fpath{test_worker_supervisor_v411.py}) cover:
\begin{itemize}
\item a normal completion; a hung worker that blocks the receipt until it is terminated; termination after a grace period; a crashing worker;
\item a late completion after termination, and a completion arriving after expiry, both rejected and discarded;
\item a terminated worker's token presented for a later request, and a duplicate completion, both rejected;
\item a kernel crash followed by restart and receipt;
\item an operating-system \code{SIGKILL} of the supervising process: the worker exits within the test's deadline, the restarted kernel holds no receipt, rejects the stale token, and accepts a receipt only after expiry and erasure;
\item a file opened by the parent is not inherited by the worker.
\end{itemize}

\paragraph{Cost of supervision.}

\paragraph{Binding and inventory records.}
Every signed object carries a domain label and format version. A recovery request binds account, request ID, active configuration, target birth epochs and generations, package/commitment digest, exact recipient key and channel binding, checkpoint reference and hold policy; approvals cover the whole object. A receipt binds account, configuration, bank, epoch, generation, holder index, capsule/commitment digest and cleanup-policy version. A checkpoint binds a fresh nonce, configuration, committed barrier digest and floor. The inventory schema records each atom's type, origin, epoch, generation, holder, bank version, disclosure interface, derivation premises and deletion contract, including worker memory as a location. The reference CBOR encoder accepts only integers, bytes, strings, arrays, maps, booleans and null, with definite lengths and bytewise encoded-key order. Certificates in the kernel are trusted verifier outputs, not signatures.
